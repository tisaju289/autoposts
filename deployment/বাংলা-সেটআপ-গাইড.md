# Auto Posts — প্রতিটি ক্রেতার আলাদা সাইট সেটআপ

## আগে গুরুত্বপূর্ণ কথা
এই প্রজেক্টের বর্তমান Lovable Cloud সংযোগ খুলে ফেলা যায় না। সেটি অক্ষত থাকবে। নতুন ব্যবস্থা দিয়ে **আলাদা ক্রেতার সাইটে** নিজের ডাটাবেস ব্যবহার করা যায়; কোনো ক্রেতার তথ্য আপনার বর্তমান সাইটে যাবে না। শুধু SQL চালালেই পুরো টুল চলবে না: সাইট হোস্টিং, লগইন, ফাইল রাখার জায়গা, AI, Google ও Facebook অনুমতি এবং সময়মতো পোস্ট করার ব্যবস্থা লাগবে।

এই ফাইলগুলোতে বর্তমান ব্যবহারকারী, পোস্ট, Facebook Token বা কোনো আসল গোপন key নেই।

## ফাইলগুলো কী কাজে লাগবে
- `fresh-install.sql`: নতুন খালি ক্রেতার ডাটাবেসে টেবিল, ব্যবহারকারীভিত্তিক নিরাপত্তা, ফাইলের অনুমতি ও গোপন scheduler token তৈরি করবে। একবার চালাবেন। বর্তমান সাইটে চালাবেন না।
- `customer.env.example`: কী কী সেটিং দিতে হবে তার খালি তালিকা।
- `scheduler.sql`: স্বয়ংক্রিয় পোস্টের 5 মিনিট অন্তর কাজ চালানোর উদাহরণ।

## 1. প্রতি ক্রেতার জন্য আলাদা ব্যবস্থা
প্রতি ক্রেতার নামে নতুন সাইটের কপি, নিজের ডাটাবেস প্রজেক্ট, নিজের URL এবং নিজের সংযোগ দিন। পুরোনো `.env`, ব্যবহারকারীর তথ্য বা আপনার গোপন key কপি করবেন না। সোর্স কোড ডাউনলোড/নিজের সংযুক্ত repository থেকে নিন; এই প্যাকেজে পুরো অ্যাপের সোর্স নেই।

নতুন ডাটাবেসে Auth, Storage এবং PostgREST/Data API থাকতে হবে। শুধু সাধারণ PostgreSQL যথেষ্ট নয়। ক্রেতার নিজের পরিষেবার SQL চালানোর পেজে `fresh-install.sql` খুলে পুরোটা চালান। আগে থেকে `posts`, `settings`, `fb_pages` থাকলে থামুন—এটি নতুন ইনস্টলেশনের জন্য, আপগ্রেড নয়।

## 2. ফাইল রাখার জায়গা
Storage-এ `post-images` নামে **Private** bucket তৈরি করুন। Public করবেন না।
- bucket-এর ফাইল সাইজের সীমা কমপক্ষে 500MB বা 524288000 bytes দিন; পরিষেবার মোট সীমাও এত বড় হতে হবে।
- JPG/PNG/WebP/GIF এবং MP4/MOV/WebM অনুমতি দিন; প্রয়োজনে MIME restriction খালি রাখুন।
- টুল নিজে ছবি সর্বোচ্চ 20MB ও ভিডিও 500MB নেয়। ছবির মূল মান কমানো হয় না।
- ফাইল ব্যবহারকারীর ID-র ফোল্ডারে থাকে; SQL সেই ফোল্ডারের অনুমতি আলাদা রাখে।
- প্রকাশের 12 ঘণ্টা পর মূল ফাইল ও তৈরি Reels মুছে যেতে পারে; মূল ডিজাইন নিজের কাছে রাখুন।

## 3. সাইটে ক্রেতার সংযোগ বসান
`customer.env.example` দেখে হোস্টিংয়ের Environment variables অংশে মান দিন:

| নাম | কী দেবেন | গোপন? |
|---|---|---|
| VITE_CUSTOM_BACKEND_URL | ক্রেতার ডাটাবেস পরিষেবার HTTPS project origin, শেষে কোনো পথ নয় | না |
| VITE_CUSTOM_BACKEND_PUBLISHABLE_KEY | একই ক্রেতার publishable key বা পুরোনো anon key | না |
| CUSTOM_BACKEND_URL | উপরের একই URL | না |
| CUSTOM_BACKEND_PUBLISHABLE_KEY | উপরের একই public key | না |
| CUSTOM_BACKEND_SECRET_KEY | ক্রেতার নিজের পরিষেবার server-only secret/service-role key | হ্যাঁ |
| GEMINI_API_KEY | ক্রেতার নিজের Gemini key | হ্যাঁ |

**গোপন key কখনো VITE_ দিয়ে শুরু করবেন না, ব্রাউজারে পেস্ট করবেন না, চ্যাটে পাঠাবেন না।** বর্তমান Lovable Cloud-এর গোপন server key নেওয়া যায় না; এই মান ক্রেতার নিজস্ব পরিষেবা থেকে লাগবে।

ব্রাউজার ও সার্ভারের URL/key একই ক্রেতার হতে হবে। আংশিক সেটিং দিলে টুল থামবে, আপনার পুরোনো সংযোগে ফিরে যাবে না। কোনো custom মান না দিলে বর্তমান Cloud-এর ব্যবস্থা চলবে।

এই অ্যাপ সাধারণ static HTML সাইট নয়। TanStack Start/Nitro সমর্থন করে এমন server hosting দরকার; বর্তমান সেটআপ Cloudflare target ব্যবহার করে। সোর্সের dependency ইনস্টল করে build/deploy করুন এবং runtime-এ server variables দিন। VITE_ মান বদলালে আবার build/deploy করতে হবে। কোনো গোপন মান build-এর public অংশে রাখবেন না।

## 4. লগইন চালু করুন
ক্রেতার নিজস্ব Auth পরিষেবায় Email signup/login চালু করুন; email confirmation চালু রাখুন।
- Site URL দিন ক্রেতার প্রকাশিত সাইটের ঠিকানা।
- Redirect allowlist-এ `https://ক্রেতার-সাইট/auth` দিন।
- Confirmation email-এর লিংক ক্রেতার সাইটের `/auth`-এ ফেরত আসবে এমনভাবে সেট করুন।
- নতুন সাইটে “নতুন অ্যাকাউন্ট খুলুন” দিয়ে অ্যাকাউন্ট তৈরি, ইমেইল কনফার্ম, তারপর Email/Password দিয়ে ঢুকুন।

আলাদা সংযোগের সাইটে Google login বাটন রাখা হয়নি; বর্তমান Cloud সাইটে আগের Google login থাকে। ক্রেতার নিজস্ব Google login যোগ করা এই সেটআপের অংশ নয়। লগইনের Google আর Drive/Sheets-এর Google অনুমতি এক নয়।

## 5. Google Drive এবং Google Sheets
আলাদা ক্রেতার সাইট আপনার Lovable workspace-এর Google সংযোগ ব্যবহার করবে না। ক্রেতার নিজের Google OAuth অনুমতি লাগবে।

1. ক্রেতার Google Cloud প্রজেক্টে Drive API ও Sheets API চালু করুন।
2. OAuth consent screen সেট করুন; Testing হলে ক্রেতার Google email test user করুন।
3. OAuth client তৈরি করুন। Offline access সহ অনুমতি নিয়ে refresh token সংগ্রহ করতে হবে। Google OAuth Playground ব্যবহার করলে settings-এ নিজের OAuth credentials দিন, এবং client-এর redirect URI-তে `https://developers.google.com/oauthplayground` যোগ করুন।
4. এই scopes নিয়ে অনুমতি দিন: `https://www.googleapis.com/auth/drive.readonly` এবং `https://www.googleapis.com/auth/spreadsheets`। নিজের credentials ব্যবহার না করলে Playground-এর token এই client-এর সঙ্গে কাজ করবে না।
5. হোস্টিংয়ের **গোপন server settings**-এ `CUSTOM_GOOGLE_CLIENT_ID`, `CUSTOM_GOOGLE_CLIENT_SECRET`, `CUSTOM_GOOGLE_REFRESH_TOKEN` দিন। Token অন্যকে দেবেন না।
6. ওই Google account যেন Drive folder পড়তে ও Sheet লিখতে পারে।
7. টুলের Settings-এ Sheet link ও আসল tab name সেভ করুন। এরপর Dashboard-এ Drive folder/file link দিন ও Sheet sync পরীক্ষা করুন।

Testing অবস্থার কিছু Google OAuth refresh token 7 দিন পর মেয়াদ হারাতে পারে; বিক্রির আগে consent/verification ও production access ঠিক করুন। অনুমতি বাতিল হলে পুনরায় নিতে হবে। এই সেটআপে প্রতিটি আলাদা ক্রেতার সাইটের জন্য একটি Google account ব্যবহৃত হয়; একই সাইটের প্রতি login-user-এর আলাদা Google সংযোগ নয়।

## 6. Facebook ও Instagram
Settings-এ ক্রেতার Facebook Page ID ও Page Access Token সেভ করুন। অন্য পেজ চাইলে “আরও Facebook Page” থেকে যোগ করুন।
- Page পরিচালনার উপযুক্ত অনুমতি দরকার: `pages_show_list`, `pages_read_engagement`, `pages_manage_posts`।
- Analytics-এর জন্য `read_insights` দরকার।
- Instagram Professional account সেই Facebook Page-এর সঙ্গে যুক্ত থাকতে হবে; `instagram_basic`, `instagram_content_publish` অনুমতি লাগবে।
- Token-এর মেয়াদ ও Meta app-এর production permission/review পরীক্ষা করুন; শুধু ID দিলেই পোস্ট হবে না।
- আগে একটি বাস্তব পরীক্ষার পোস্ট দিন; Feed, Story, Reels আলাদা ফলাফল দেখুন।

## 7. স্বয়ংক্রিয় পোস্ট চালু করুন
নতুন ডাটাবেসের extensions settings থেকে `pg_cron` ও `pg_net` চালু করুন। তারপর `scheduler.sql`-এ `https://YOUR-CUSTOMER-SITE` বদলে ক্রেতার **প্রকাশিত** সাইটের ঠিকানা দিয়ে SQL চালান। এটি প্রতি 5 মিনিটে গোপন token সহ POST পাঠায়। Token ফাইলে লেখা বা প্রকাশ করার দরকার নেই।

একই job বারবার তৈরি করবেন না। cron job ও HTTP response দেখে 200 আসছে নিশ্চিত করুন। 401 হলে গোপন token/অন্য প্রজেক্ট সংযোগ মিশেছে; 500 হলে সাইটের server settings পরীক্ষা করুন। প্রতি চালনায় সর্বোচ্চ 10 due post প্রসেস হয়। সাইট/ডাটাবেস বন্ধ বা quota শেষ থাকলে সময়মতো পোস্ট হবে না; ঠিক মিনিটে প্রকাশের নিশ্চয়তা নেই।

## 8. 15 সেকেন্ডের Reels ও আগে থেকে শিডিউল করা পোস্ট
একই ছবি থেকে আলাদা গানসহ 15 সেকেন্ডের ভিডিও তৈরি হয়। মূল ছবি ও অনুমোদিত ক্যাপশন অপরিবর্তিত থাকে। নতুন শিডিউল/এখনই পোস্ট দেওয়ার আগে ভিডিও প্রস্তুত করা হয়।

আগে থেকে শিডিউল করা পোস্টের পুরোনো ছোট Reels-ও বদলানোর ব্যবস্থা আছে: Dashboard খুললে আপনার **সব পেজের** অপ্রকাশিত ছবির পোস্টগুলো একে একে প্রস্তুত হয়; পেজ বদলাতে হবে না। **প্রস্তুতি শেষ না হওয়া পর্যন্ত ট্যাব খোলা রাখুন**, এবং শিডিউলের আগে “15 সেকেন্ড প্রস্তুত ✓” দেখুন। ছবি থেকে ভিডিও তৈরির কাজ ব্রাউজারে হয়; বন্ধ ট্যাবে বা শুধু cron দিয়ে ভিডিও তৈরি হবে না। সময় চলে এলে অসম্পূর্ণ Reel-এর কারণে Feed/Story পুনরায় প্রকাশ করা হয় না; Reel আলাদা ব্যর্থতা দেখাতে পারে।

## কী এখনো বাস্তবে পরীক্ষা করতে হবে
নতুন ক্রেতার URL, private key, Google অনুমতি ও hosting না থাকায় এই প্রকল্প থেকে নতুন আলাদা ইনস্টলের পুরো live পরীক্ষা করা যায়নি। আপনার বর্তমান ডাটাবেসে fresh-install SQL চালানো হয়নি—পুরোনো তথ্যের নিরাপত্তার জন্য। বাস্তব Facebook/Instagram-এ পরীক্ষামূলক পোস্টও অনুমতি ছাড়া দেওয়া হয়নি। শুধু ডাটাবেস সংযোগ দিলেই সব বাহ্যিক পরিষেবা স্বয়ংক্রিয়ভাবে যুক্ত হয় না।
